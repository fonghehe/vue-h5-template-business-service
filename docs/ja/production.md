# 本番動作とアップグレード

階層化された Go モノリスを維持します。Handler は HTTP、バインド、DTO 変換、Service は業務規則とトランザクション境界、Repository は Context 付き SQL を担当します。AI ストリーミングは別サービスです。既存 `/api` と JSON フィールドは互換性を保ち、`/api/v1` にも同じ業務 Handler を登録します。両方のルートでレート制限を共有し、cookie はログインした認証プレフィックスに限定します。

## 既存環境の更新

1. 専用 PostgreSQL データベースをバックアップし、復元したコピーで検証します。
2. 新しいバイナリと確認済みの設定で `make migrate-status`、`make migrate` を実行します。
3. 追加移行で `refresh_sessions` と取引の制約・インデックスを作成します。不正な既存データは移行を失敗させます。制約を外さずデータを調査してください。PostgreSQL のトランザクション advisory lock は同一 DB/schema の移行を直列化し、失敗時は未適用バッチ全体をロールバックします。破壊的な自動 down はありません。検証済みバックアップの復元またはレビュー済み前進修正を使います。
4. `AUTO_MIGRATE=false`、`SEED=false` でレプリカを起動します。未適用移行があれば HTTP を開始しません。staging/production はこの既定値です。開発環境は起動時移行と seed を維持し、seed は排他実行で空テーブルだけを補います。
5. 既存 Access JWT は有効なアカウントなら使えます。旧 Refresh JWT には保存済みセッションがないため再ログインが必要です。フロントエンドの公開と調整してください。

移行 ID は日付ではなく連番と意味のある名前（例：`004_extend_product_catalogue`）を使います。既存の日付付き台帳記録も適用済みと認識され、手動の書き換えは不要です。新しく適用する移行は新 ID を記録します。今後の変更は追加し、公開済みの処理を変更・再利用しないでください。

## 認証とブラウザーの境界

PostgreSQL は Refresh JWT の SHA-256 ダイジェストだけを保存します。更新は有効セッションを一度消費し、同一トランザクションで置換します。同時更新は一件だけ成功します。ログアウトは提示された更新セッションを失効させ cookie を削除します。Access JWT は有効期限までステートレスであり、クライアントで破棄してください。全端末ログアウトやトークンファミリーの盗難検出は含みません。盗まれた新トークンは失効・期限切れまで使用できる可能性があります。

認証済み業務リクエストごとに現在のアカウント状態とロールを読み込みます。無効化や admin 削除は次回要求から反映されます。独立 AI サービスにも対応する方針が必要です。現在の `user` / `admin` は既存 API 向けで、動的権限テーブルや権限管理 UI は追加していません。

ブラウザーは credentials と cookie を送り、更新要求を直列化します。許可した Origin のみ受け付け、Origin のない非ブラウザー要求もサポートします。CORS は認証の代わりにはなりません。更新/ログアウトは任意の JSON `refreshToken` に対応します。cookie 使用時も不正 JSON や後続 JSON は 422 です。

## リソースと運用の制限

- `REQUEST_TIMEOUT=10s` は協調的 deadline を SQL/キャッシュへ伝え、期限切れは HTTP 504 / code 5040。`WRITE_TIMEOUT` より短く設定します。Context を無視する CPU 処理を強制停止したり、確定済み取引を取り消したりはできません。決済注文の再試行は同じ冪等キーを使います。
- Body 上限はチャンク転送・後続データを含め 1 MiB、ページ上限は 50。インスタンス内 limiter は最大 10,000 クライアントを保持し、満杯時は新規クライアントを拒否、アイドル記録の失効後に回復します。認証ルートは追加で毎秒 0.5、バースト 5 を共有します。複数レプリカはエッジで共有防御を設定し、任意の転送 IP ヘッダーは信頼しません。
- `/metrics` は HTTP 件数/時間、業務カウンター、DB プール、Go ランタイムを提供します。プロセス指標はプラットフォーム対応に依存します。JWT はなく、内部ネットワークまたはプロキシで制限します。OpenTelemetry エクスポーターと追跡バックエンドは未設定です。
- SQL エラー/遅いクエリ時間は requestId 付き構造化ログに記録し、SQL 本文・バインド値は出力しません。Context メタデータは Gin 非依存です。Worker は期限切れセッションを有限バッチで削除し、注文を個別取引で失効処理してキャンセルに応答します。シグナルで Worker をキャンセルし、HTTP ドレイン後に終了を待ってからキャッシュと DB を閉じます。
- Redis は任意の商品キャッシュです。接続・プール・コマンド待機を制限し、deadline を尊重、再試行を無効化し TTL に jitter を加えます。在庫は常に PostgreSQL から取得します。キャッシュヒット時にも DB の販売・削除状態を確認し、無効化に失敗しても非公開・削除済みの商品を公開し続けないようにします。無効化は best effort で、障害や並行再充填では TTL まで古い商品値が残る場合があります。Redis は降格できるため readiness は PostgreSQL を確認します。

## 本番イメージの起動

通常の `docker-compose.yml` は開発用のままです。独立の本番定義は環境変数と専用 DB を要求します。

```bash
docker build -t vue-h5-template-business-service:local .
# DATABASE_URL / JWT_SECRET / MOCK_PAYMENT_WEBHOOK_SECRET / CORS_ORIGINS
# をデプロイ環境で設定し、開発シークレットを使わないでください。
docker compose -f compose.production.yml run --rm migrate
docker compose -f compose.production.yml up -d business
```

ホストポートは localhost 限定、非 root・読み取り専用 FS・capabilities 削除で実行し、上流 TLS プロキシが必要です。本番ユーザー、証明書、DB バックアップ、監視保存先は作成しません。イメージには `/app/server` と `/app/migrate` を含み、プローブは `/health` と `/ready` です。

## 商用決済の境界

決済 Provider はシミュレーターで、実資金を決済しません。本番には事業者固有の署名検証、長い DB 取引の外での冪等な外部決済作成、callback 再試行方針、照合と返金が必要です。業務要件のない MQ、Cron 基盤、未使用外部 Client 抽象は追加しません。

更新セッションの有効期限は PostgreSQL の行ロック取得後に再確認し、待機中に期限切れになった場合は更新しません。HTTP 更新は認証情報が無効またはアカウントが無効化された場合のみ cookie を削除します。内部障害・タイムアウト・キャンセルでは再試行用に保持しますが、更新コミット後の応答紛失では再ログインが必要になる場合があります。標準 HTTP method の指標ラベルは維持し、拡張 method は `OTHER` にまとめて Prometheus の系列増加を制限します。
